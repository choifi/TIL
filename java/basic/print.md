# System.out.println 절대 사용하지 않아야 하는 이유가 뭘까?
실무 환경, 특히 고성능 백엔드 시스템에서 System.out.println을 절대 사용하지 말라고 강조하는 이유는 시스템의 '처리량(Throughput)'과 '안정성'에 치명적인 영향을 주기 때문입니다. 

# 1. System.out.println의 내부 구조 : synchronized
자바의 System.out은 PrintStream 객체입니다. 이 객체의 내부 코드를 뜯어보면 모든 출력 메서드가 아래와 같은 구조를 가지고 있습니다. 
```java
    public void println(String x) {
        synchronized (this) {
            print(x)
            newLine();
        }
    }
```
* 임계 구역(Critical Section): 한 스레드가 로그를 출력하는 동안 PrintStream 객체에 잠금(Lock)을 겁니다. 
* 병목 현상: 멀티 스레드 환경(예: WAS)에서 수많은 스레드가 동시에 로그를 남기려 하면, 다른 스레드들은 앞선 스레드의 출력이 끝날 때까지 줄을 서서 기다려야 합니다. 이는 CPU 자원을 효율적으로 쓰지 못하게 가로막는 주범이 됩니다.

# 2. 하드웨어와의 만남: Blocking IO
로그는 결국 터미널 콘솔이나 파일 같은 '외부장치(I/O)'에 기록됩니다. 
* 커널 대기: 애플리케이션이 출력을 요청하면 운영체제의 커널에 쓰기 작업을 요청합니다. 이때 하드웨어 장치의 처리가 끝날 때까지 해당 스레드는 'Blocking(차단)' 상태가 됩니다. 
* 속도 차이: CPU의 연산 속도에 비해 디스크나 네트워크, 콘솔 출력 속도는 현저히 느립니다. println을 남발하면 고성능 서버가 저속 I/O 작업에 발이 묶여 전체 응답 시간이 길어지는 현상이 발생합니다. 

# 3. Logback이나 Log4j2는 왜 괜찮을까? (비동기 로깅)
전문적인 로깅 프레임워크를 사용하면 이러한 문제들을 우아하게 해결할 수 있습니다. 
* 비동기 처리 (Appender): 스레드가 직접 I/O를 수행하지 않고, 로그 메시지를 메모리상의 '큐(Queue)'에 빠르게 던져놓고 즉시 자기 일을 하러 돌아갑니다. 실제 기록은 별도의 전용 스레드가 나중에 처리합니다. 
* 로그 레벨 관리: System.out.println은 한 번 작성하면 삭제하기 전까지 계속 실행되지만, 로깅 프레임워크는 설정 파일 하나로 실무(Production) 환경에서 불필요한 로그 출력을 완전히 끌 수 있습니다. 

  구분      |      System.out.println           |   Logging Framework (Async)
  동기화     | synchronized로 인한 스레드 경합 발생   |  락 프리(Lock-free) 또는 최소화된 동기화 
  I/O 방식  | 동기식 Blocking IO (응답 지연 유발)    | 비동기식 처리 (성능 저하 최소화)
  유연성    | 코드 수정 없이는 출력을 제어할 수 없음     | 설정만으로 로그 레벨 조정 가능
  정보량    | 메시지만 출력됨                       | 날짜, 시간, 스레드명, 클래스명 등 포함
